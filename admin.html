OWNERSHIP & PUBLISHING

The public site is
read-only by design.

Visitors can read, practise and track their own progress, but nothing they do in the browser can change the published lessons. Editing happens in a local studio on the owner's computer, and publishing happens through git.

Why there is no password here. A password checked in the browser is not real security: anyone can read the JavaScript or edit the page locally. The honest boundary is file access and repository access, not a password box.

Who can change what

RoleCan doCannot do
Visitor Read lessons, use flashcards, keep progress in their own browser. Change published content or other people's progress.
Owner Edit locally in the studio, build, commit and push to main. —
Contributor Fork the repository and open a pull request. Push directly to main or publish without review.

Edit locally in the studio

  1. On the computer, run npm install once, then npm run dev.
  2. Open the studio. Edits are stored in that browser only until you export or commit them.
  3. Write Markdown, preview the KaTeX formulas, and check the print layout.
  4. Use Download .md to save a chapter, or copy the content into the matching file under chapters/class-9/.
  5. Refresh the site pages to confirm the lesson, flashcards and formula vault all agree.

Browser storage is not a backup. Clearing site data erases studio edits. Export or commit anything you want to keep before clearing the browser.

Publish through git

From the project folder on the computer:

git status
git add .
git commit -m "Describe the lesson change"
git push origin main

The push triggers the GitHub Actions workflow, which builds the site and deploys it to GitHub Pages. Check the Actions tab for a green run, then reload the live URL. If the run fails, the previous deployment stays live.

Contributions go through review

The main branch is protected. Collaborators cannot push to it directly; they must open a pull request and receive approval. A pull request merged by the owner is the approval gate. This keeps the published lessons stable while still letting people suggest corrections.

  1. Contributor forks the repository and makes the change on a branch.
  2. They open a pull request describing the correction and the source.
  3. The owner reviews the maths, the wording and the build.
  4. The owner merges; the deploy workflow publishes the approved version.

For a small correction, an issue with the exact page and suggested wording is enough. Do not paste personal data into an issue.

Flashcard ids are based on deck order. Add new cards at the end of a deck so existing per-device review schedules keep pointing at the right card.

Export the book

The studio can export the whole course as a fixed-layout EPUB with facing pages, for Apple Books on iPad, and print an A4 PDF. Both exports use the same pagination as the web reader, so a page break you fix in one place appears everywhere.

A spread EPUB needs a landscape screen and rendition:spread enabled, which the export sets. On a narrow phone screen, Apple Books will show one page at a time; that is expected.

Installing on iPad

  1. Open the live site in Safari.
  2. Tap Share, then Add to Home Screen.
  3. Launch it from the home screen and let the first visit cache the pages.
  4. After that, lessons open offline. Progress and flashcard schedules stay on that device.
